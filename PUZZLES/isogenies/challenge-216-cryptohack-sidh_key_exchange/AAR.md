# AAR — challenge-216: SIDH Key Exchange (cryptohack.org, 80 pts)

**Status:** SOLVED, submitted live 2026-10-21. Score 11400 → 11480 (201 solved).

## Problem
`source.sage` gives p = 2^110·3^67 − 1, F = GF(p²) with i² = −1, E0: y² = x³ + x,
torsion generators P2,Q2 (order 2^110) and P3,Q3 (order 3^67), secrets sA, sB, and
`gen_public_key`/`gen_shared_secret` stubbed out. Flag = AES-CBC-SHA256(str(shared_secret)).

## Approach
No Sage on this host; sympy/fpylll paths for F_{p²} elliptic arithmetic were too slow
for a 110+67-step walk. Chose **PARI/GP 2.17** (`~\tools\gp64.exe`) which has
native `ellisogeny` (Vélu) + `ellisogenyapply` over `t_FR` (ffgen) fields.

Pipeline (`gen_gp2.py` → `gpsidh.gp` → `decrypt_gp.py`):
1. Field: `f2 = ffinit(p,2,'x); w = ffgen(f2,'w)`. Recover the sage i-basis inside gp:
   D = a1²−4a0, β = √(−4/D), α = a1·β·((p+1)//2), i_gp = α + β·w (check i_gp² = −1).
2. RA = P2 + sA·Q2, RB = P3 + sB·Q3 (`elladd`/`ellmul`).
3. `chain(E,R,ell,e,extras)`: e sequential degree-ℓ steps — Q = [ℓ^(e−i)]R,
   iso = `ellisogeny(E,Q)`, map R and the tracked extras (P3,Q3 / P2,Q2) with
   `ellisogenyapply`, E = ellinit(iso[1]).
4. EA = chain(E0,RA,2,110,[P3,Q3]); EB = chain(E0,RB,3,67,[P2,Q2]);
   EAB = chain(EB, P2B+sA·Q2B, 2, 110, []); EBA = chain(EA, P3A+sB·Q3A, 3, 67, []).
5. j computed manually as 6912·a4³/(4a4³+27a6²); **jAB == jBA** (self-check, no MISMATCH).
6. gp prints j in the w-basis + α,β; Python converts to i-basis (jimag = v/β,
   jreal = u − vα/β), builds `"{jimag}*i + {jreal}"` (sage str format), SHA256 → AES-CBC
   decrypt → flag on the first variant.

## gp 2.17 pitfalls (cost most of the time; all Observed on this build)
- `ellj()` rejects curves over F_q (t_FR coefficients) → compute j from a4,a6 by hand.
- `for(i=a,b, s1; s2)` multi-statement bodies are a **parse error** (even single-line).
  Workaround: put the body in a function and use the `if(1, s1; s2)` single-expression idiom.
- Destructuring `[a,b] = f()` inside a `for` body mis-parses → use `iso[1]`, `iso[2]`.
- Trailing `;` before the closing `)` of `for(...)` is a parse error.
- `t_FFELT` (lift of t_FR) has no usable `polcoeff`/`lift`-to-integer path → parse the
  printed `A*w + B` form in Python instead.
- Python f-strings generating gp code must be **raw** (`rf"""`), else `\\` comments
  collapse to `\` and gp dies; `{`/`}` in f-strings need doubling.
- `lift(sqrt(Mod(-4,p)/(Mod(D,p))))` for the √; `((p+1)\ 2)` for integer division.

## Vulnerability (plain words)

None — the challenge hands you both secrets sA, sB and asks you to run SIDH
honestly: perform Alice's 2^110-step walk and Bob's 3^67-step walk from
E0: y² = x³ + x over F_{p²}, p = 2^110·3^67 − 1, carrying the other party's
torsion images along. The shared secret is the j-invariant of the corner curve of
the SIDH diamond; the "math" is that the diamond commutes.

## How the answer follows

- A walk = e sequential Vélu ℓ-isogenies with kernels generated by
  Q = [ℓ^{e−i}]R, R = P2 + sA·Q2 (resp. P3 + sB·Q3). At walk end the far side must
  still be able to continue, so the auxiliary torsion points (P3,Q3 resp. P2,Q2)
  are transported through every step with ellisogenyapply — this is what makes the
  corner walks with P2A + sA·Q2A possible at all.
- SIDH diamond correctness (Kani–Rosen commutative-square intuition): the two
  composed walks, 2^110-then-3^67 and 3^67-then-2^110, land on isomorphic corner
  curves, hence j(E_AB) = j(E_BA). The script asserts exactly this equality and
  it held — a real end-to-end check of the whole 177-step pipeline with no
  external oracle.
- Shared secret = that j, serialized in Sage GF(p²) notation `im*i + re`. PARI
  prints j in its ffgen w-basis, so a basis change recovers the i-basis:
  reconstruct i = α + βw, then j_im = v/β, j_re = u − vα/β.
  key = SHA256(str(j)) → AES-CBC → [flag — recorded in FLAGS/isogenies/challenge-216-cryptohack-sidh_key_exchange/flag.txt].

## Limitations / attempts that failed

- sympy/fpylll routes for F_{p²} EC arithmetic were ruled out on speed before the

- Most time was lost to gp 2.17 friction, not math: ellj rejects t_FR curves (j
  by hand from a4,a6); multi-statement for-bodies are parse errors (worked around

  t_FFELT lift dead-end (parsed the printed `A*w + B` in Python instead);
  f-string escaping killed the first gp generator.
