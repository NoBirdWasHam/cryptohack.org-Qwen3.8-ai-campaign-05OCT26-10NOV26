# CTF AAR corpus publication workflow

Use when bringing an AAR corpus to audit/publication standard, reconstructing missing AARs, prepping a corpus for upload/handoff, or building the publishable campaign repo (sanitized tree + PII gates + flag ledger). Solve-side doctrine (flag provenance, source disclosure) lives in the campaign SOLVER_BRIEF.md; this skill is the corpus mechanics.

## Hard rules (every batch)
- Append-only remediation: never alter existing bytes, claims, flags, or verdicts. Hash old content pre/post to prove the append (byte-prefix check); keep the hashes as batch evidence.
- Write-ups must state evidence limits honestly: 'not recorded in run logs' / 'recovery procedure not recorded' beats a reverse-engineered plausible story. Marking HOW-impossible is a pass, not a failure.
- Negatives are skill maps, not shame lists: OPEN/NEGATIVE AARs keep exact counts, proofs, and bounds; never soften or pad.
- Editor units are offline-only: no re-running challenges, no touching solve scripts, no new solves or submissions.

## Falsifying decisive-negative AARs (validation units)
- Before believing a NEGATIVE verdict hinged on artifact data quality, byte-diff the archived instance against the live static file AND the organizer's public repo copy (CryptoHack ctf-archive category HTML carries each challenge's `/static/challenges/<file>_<hash>` links; the source CTF repo, e.g. DownUnderCTF/Challenges_2020_public, ships the identical output plus often an official exploit.sage and flag). Data matching all three = canonical; the bug is in our pipeline, not the data.
- A negative that priced only the GENERIC formulation (e.g. bivariate Coppersmith on a sqrt-sum hint) must be re-checked against the author's planted path before finalizing: fetch the organizer writeup/repo solution and record it as the technique source.

## Indexer header gotcha
- Legacy AARs using numbered headers (`## 4. How it was solved`, `## 7. Limitations`) FAIL the indexer's HOW/LIM regexes (they require `## how`/`## limitations` adjacency). Clearing the queue means APPENDING the exact un-numbered doctrine headers, not judging the numbered content as missing. The `failed`/`didn't work` LIM alternatives match anywhere in the body, so a LIM flag can be a false pass — check which header matched.

## Publication sections
SOLVED: '## Vulnerability (plain words)' (2-4 sentences, the mechanism, not click-narration), '## How the answer follows' (derivation steps with the key numbers from AAR/scripts), '## Limitations / attempts that failed', '## Sources' (cited refs, or 'self-derived per logs').
OPEN/NEGATIVE: '## The challenge (plain words)', '## Current state of the attack', '## What has been ruled out and why', '## Sources'. The indexer's HOW regex must accept these negative headers, or OPEN AARs can never clear the quality queue. Same for the LIM regex: batch #9 (2026-11-02) extended aar_index.py's LIM regex to accept `## what has been ruled out` — without it, task-mandated negative vocabulary never clears the gate. Note LIM also matches the word `failed` in prose ANYWHERE, so prose-only lim=True is common; gate the HOW header only. When a gate fix reclassifies other units' folders, list them in the batch report (honest queue delta).

## Batch procedure
1. Regenerate the index (`python3 aar_index.py` → AAR_INDEX.md + aar_index.json). Its 'Remediation queue' lists folders missing HOW/LIM or lacking an AAR; take the queue head as this batch (~9-14 folders per unit).
2. Dispatch editor subagents with DISJOINT folder lists (parallel batches are safe; index regeneration is idempotent — tell each unit concurrent batches exist).
3. Every editor brief must carry: doctrine sections to read first, the exact section vocabulary, append-only + byte-prefix rule, 'not recorded in run logs' rule, call budget (~35-45), deliverable = per-folder one-liners + queue delta, regenerate index at end.
4. Verify the claimed queue delta with your OWN aar_index.py re-run before reporting it.
5. NO-AAR folders are a separate RECONSTRUCTION class: evidence order = ledger notes (progress.json) → folder solve scripts/logs → statement. Scripts evidence the method but do not extend its HOW past what the script shows. Mark output '## RECONSTRUCTED AAR (post-hoc)'.
6. Missing flag.txt on a SOLVED folder: restore from the flag verbatim in the ledger/AAR (provenance = ledger/solved-list, not fresh retrieval — legitimate housekeeping).
7. Wall-map AARs that grew past ~10k chars across runs: append a plain-words state summary at the TOP so a fresh session reads the state in one screen.

## Near-duplicate folder names
- Mirror folders can differ by ONE typo character (e.g. `srateslla` vs `sratslla` for one challenge): `ls` renders them as identical duplicates. Hex/byte-compare folder names before assuming a listing glitch — the canonical solve may live in the misspelled twin while the correctly-spelled one holds an earlier partial-attempt record whose text contradicts the ledger status (indexer status is keyed by slug, so the ledger SOLVED override rides on both).

## Ledger hygiene
- Folder mirrors (one challenge living in two folders, e.g. canonical solve vs server-artifact stub): annotate canonical attribution on the ledger row so audits count one credit; the indexer keys status by slug, so the stub shows the real status — the stub's AAR text must say so.
- Editor upgrades that re-check arithmetic (verifying a j-invariant, re-deriving a rational) are comprehension checks: disclose them in Sources as upgrade-time checks, never as new solves.

## Read-only audit procedure (no writes to the tree)
The corpus carries THREE ledgers with DIFFERENT key spaces — reconcile by slug, and expect the counts to differ:
- `progress.json` queue: one entry per LIVE site challenge, keyed by SITE slug; status `solved`/`open`; carries `flag`, `notes`, `folder`.
- `aar_index.json`: one entry per AAR, keyed by FOLDER-style slug (`challenge-NN-cryptohack-...`); status `SOLVED`/`OPEN`/`NEGATIVE`; the `name` field is often EMPTY — a name-set diff produces a garbage result (every entry "missing"); match on slug/folder.
- `AAR_INDEX.md`: human table, should be 1:1 with the JSON; row count is the cross-check.
Folder count > queue count > index count is EXPECTED, not corruption: the delta = duplicate/variant folders (see Near-duplicate folder names) plus root-level extra copies of a challenge. Explain every audit delta by naming the duplicates; under a read-only audit report, never fix.
- Hash check: aar_index.py hashes NORMALIZED text (UTF-8 read, universal newlines → LF, re-encoded, first 16 hex of SHA-256), NOT raw bytes. A raw `sha256sum` mismatch vs the index is expected — re-hash with the same normalization before calling any AAR modified.
- Verify saved `api_*.json`/dump files actually parse as JSON before treating them as ground truth — saved HTTP error pages (404s) masquerade as dumps; an unparseable dump is non-authoritative, not a source.
- Status-contradiction checklist per entry: (a) progress.json status vs (b) aar_index.json status vs (c) flag file on disk vs (d) AAR Result wording. Any divergence is an audit FINDING (e.g. flag on disk + AAR says unsolved + index SOLVED + queue open) — report it; only the owner's ruling closes it.
- Mirror folders for one challenge can carry DIFFERENT statuses (SOLVED vs NEGATIVE): the indexer keys by slug, so both rows exist. Flag the contradiction, don't pick a winner.
- When the audit is followed by "math sources for the open puzzles": map each open entry's `notes` (they already encode the attack family) to canonical references — papers, books, tools — and pair each with its public-solution availability. Verify every citation before listing it (see the citation pitfall in `ctf-practice-runs`); an unverified reference in a publication-bound corpus is a provenance failure.

## Publishing the full campaign repo (working corpus -> public tree)
Owner's standing shape requirement (binding, schema v2): the repo must be followable by an AI OR a human — verifiable, recreatable, sourced, PII-free, and every puzzle INDEPENDENT. `PUZZLES/<category>/<puzzle>/` carries its AAR + all our scripts self-contained; authors' artifacts are linked, never re-hosted; `FLAGS/<category>/<puzzle>/flag.txt` mirrors the puzzle path exactly, and `FLAGS/INDEX.jsonl` pairs puzzle<->flag with sha256 + provenance + date (parallel paths make the pairing a path lookup; flag separation is organization, not concealment — values, dates and classes stay published). `SKILLS/` holds the skills learned; all campaign-wide docs live under `SUPPORT/`; the main README is a plain project page carrying dated screenshots. Failures publish as closed-unsolved with root cause; a FRICTION ledger stays separate from the AARs. Two records per puzzle are binding: the human `AAR.md` narrative AND an AI/LLM-optimized `AGENT.md` twin — YAML frontmatter facts (puzzle/url/date/status/flag_ref/flag_sha256/skills), the procedure mechanically extracted from the AAR's solve section, epistemic tags (OBSERVED = artifact in dir / NOT OBSERVED = not recorded), never a flag value; regenerate it from the AAR so it carries no extra facts. The README links a machine-regenerated per-puzzle VERIFICATION checklist where every flag row earns its check (see Audit pass below).
1. Collect ALL structural decisions in ONE clarify call before building (repo name/visibility, flag scope, score-clearing method+timing, username handling, re-host-vs-link-only), recommended option first.
2. Write the generator script FIRST and ship it in TOOLS/ — the tree must be re-derivable, and the generator is part of the audit story. Include policy = whitelist of OUR artifact filename families (solve*, probe*, dbg*, attack*, *_test, AAR.md, site.md, small logs; note scripts hide under many prefixes — dry-run and inspect zero-kept dirs before trusting a whitelist). Exclude policy = hard-exclude authors' artifact names (statement.txt, flag.txt, chall*.py / chal.py / challenge.py, source_provided.py, source.sage, output_provided.txt, server.py, Dockerfile, task.txt) plus noise (html/png/zip/pyc/api_*.json). Per-file size cap. CAVEAT: if the generator itself ships, it must carry zero host identity — corpus/output paths via env vars, and sanitizer regexes generalized (`Users[\\/]+[A-Za-z0-9._-]+`), because the sanitizer's own pattern strings leak the identity they were written to scrub.
3. LEDGER copy = flag-field-stripped; split the master flag ledger into the mirrored per-puzzle `flag.txt` files + `INDEX.jsonl` (metadata + sha256, no flag values inline). Rows whose flag was ledger-redacted (value stored as `crypto{...}`) publish as null + note — never reconstruct. Course/completion rows carry no flags by platform design: state that explicitly so the count does not read as corruption.
4. PII sweep AFTER copying, over the whole output tree: machine hostname (obtain via `hostname`, scan it as a literal token), account aliases, real home paths (`C:\Users\<name>`, `/c/Users/<name>`, `/home/<name>`), emails, MACs, invite tokens, and live CSRF tokens scraped into page-cache notes (`_csrf_token: "<long alnum>"` — scraped platform pages carry them; REDACT). Third-party player handles -> role-preserving pseudonyms (SOLVER-A..D / MAINT-ACCOUNT) so analyses read identically while citing the public solves URL instead of names. Re-sweep case-insensitively (a case-sensitive replace leaks Hyperreality/HYPERREALITY variants). CRITICAL: the sweep runs at build time ONLY — any later manual sync of a canonical (raw) file into the publish tree re-introduces every handle; re-apply the full substitution set to each synced file AND re-run the whole-tree scan before committing the sync. Keep the canonical corpus raw and the published tree swept, and treat 'copied then forgot' as the known failure mode of manual syncs. Deliberate keeps to document in the gates file: published author attribution (citation is not PII), RFC-reserved `.example` addresses that are challenge fiction, username-free path templates (`/c/Users/.../f.py`), and the campaign account name when the owner chose to keep it.
5. Verify scan hits BY SAMPLING before mass-redacting: number-shaped regexes (phones) hit prime factors and CTF pads; the email regex hits fictional task addresses. Redact categories that are real, after inspection — never act on raw hit counts.
6. Screenshots/images get their OWN gate — regex cannot scan pixels. Pixelate identity regions, then run an independent vision/OCR verification pass that must QUOTE any readable handle or fragment; iterate until it answers NONE. Budget at least one verify→re-redress→re-verify loop because first-pass boxes miss: identity living in message-BODY text (inline @mentions) survives header/avatar boxes; the first table row leaks when a column box starts below the header (cover from the header line down); case-insensitive re-scan catches pseudonym variants a case-sensitive replace leaked. Exclude outright any image that cannot be redacted without losing its point. Full recipe incl. the PIL function and the verify prompt: `references/media-redaction.md`.
7. Write the gates doc LAST, after every remediation pass, and regenerate it if any sweep follows — a gates file written mid-build goes stale and ends up reporting pre-sweep counts as PASS (contradicting its own final scan). Name the image gate explicitly there (OCR verification pass, not a text scan).
8. Fill doc placeholders with targeted `.replace()`, never `str.format()` — doc text containing literal braces (flag examples, code snippets) crashes format with opaque index errors.
9. Commit locally with the pseudonymous identity. First publish: one full push once the owner has cleared the platform score (owner may direct the agent to do create+push itself — browser path in the github skill, `references/browser-github-access.md`); verify anonymously after (API `private:false`, `size>0`, remote HEAD == local commit). Follow-up updates may batch per category with owner reclearing (BATCHES.md).

## Audit pass before publish (verify-then-check)
When the owner orders "verify the AARs and methods, then put in the flag like a checklist": audit FIRST, check flags ONLY on rows that pass, and never relax a gate to hide a lone outlier — leave that row FAIL with its reason printed.
- Build the checklist as a machine artifact regenerated from the tree itself (`SUPPORT/VERIFICATION.md` + machine twin `PUZZLES/index.json`): per-puzzle gates = AAR present ≥15 lines · a solve/method/vulnerability/exploit section with real substance (≥120 chars; print the measured length, warm-ups legitimately have short methods) · AGENT twin carries an extracted procedure · flag sha256 MATCHES `FLAGS/INDEX.jsonl` or the row is an honest null with recorded reason · zero PII and zero real-flag strings in prose/code. Summary counts computed, never asserted.
- Flag separation: values live ONLY under `FLAGS/`. Expect hundreds of leaked occurrences in old AARs and solve logs — purge to a pointer line and rewrite `## The flag` sections to the FLAGS path. The scrub pass and the verification pass MUST share one classifier (fakes/placeholders/code-fragments policy-listed); two drifting lists manufacture false fails. Flag-shaped strings that are real values under ledger redaction are redaction leaks — scrub them from prose even though the ledger row is null.
- Placeholder flag files (`crypto{???…}`) are dishonest verified rows even when the hash verifies. Resolve each: numeric/short course answers are legitimate answers — restore the ledger-era value; real flags restore ONLY where a contemporaneous corpus record holds exactly one unmasked candidate, with a dated provenance note in INDEX; otherwise delete and publish null+note. Nothing fabricated, nothing masked silently kept.
- Hash integrity on a Windows build host: write `.gitattributes` (`* text=auto eol=lf`) and `core.autocrlf false` FIRST — autocrlf checkout byte-rot silently breaks every published sha (working bytes grow CRLF while INDEX hashes predate publication). Canonical flag bytes = value + single LF; recompute ALL INDEX hashes from the published bytes after renormalizing, and dedupe exact-duplicate INDEX rows (same ledger row ingested twice).
- Artifact completeness: filenames cited inside an AAR must exist in its dir — extract citations (`\b[\w.-]+\.(py|log|json|txt|gp|sh|sage)\b`), copy missing ones from the working corpus through the sanitizer (size cap, authors'-name exclusions), and name oversize skips in the machine index so the gap is documented, not hidden.
- PII regex pitfalls: alias matches need case + word boundaries (a bare case-insensitive GPU-alias substring matches ordinary English words containing it — false hits poison the gate); path patterns must cover `C:\Users`, `/c/Users`, AND `/home/<user>` (copied shell scripts leak the latter). Found leaks are fixed by sanitizer SUBS, and the sanitizer that ships must stay identity-free.
- Gate amendments land as a dated addendum to GATES.md (new gates G7+, fixed bugs listed in the open); never rewrite the original gate report. Same for standing state changes: a cleared scoreboard gets a dated README line pointing at the live profile, and end-state screenshots stay labeled as dated history.
- Housekeeping the audit typically surfaces: stray root-level duplicates of category dirs from an older layout, Windows-reserved-name junk (`nul` — delete via `\\?\`-prefixed path), stale counts in README/GATES — reconcile every count to a fresh count over the tree before committing.

## Public-solve status (corpus attribute)
Public-solve availability is a corpus attribute for publication value and practice-value triage — full recipe in `references/public-solve-verification.md` (category set, parsing anchors, ledger↔site matching, third-party writeup search).
- The only usable public source is the category pages' per-row `N Solves` / `N Solutions` counts. `/solutions/` is a limited landing view; per-challenge solution pages are completion-gated (login + solved).
- Report two layers: (1) site solutions per challenge; (2) for the zero-site-solution set, third-party writeup availability per source CTF in calibrated vocabulary (Observed / Not observed / Unknown), location cited.
- Cataloging contaminates: writeup-search snippets routinely contain FULL solution text. Record locations only; flag to the owner that a puzzle with a confirmed public writeup is no longer cleanly self-solvable.
